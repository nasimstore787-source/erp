# نقطة البيع على الهاتف — API + واجهة React (RTL)

الطبقة الأولى فوق قاعدة ERP V2.1. كل منطق المحاسبة والمخزون يبقى في القاعدة (دوال `post_*`)، والـ API لا يكتب جداول الدفتر بنفسه.

## التشغيل (تطوير)

```bash
db/make_demo.sh                       # قاعدة erp_demo: شركة DEMO، المستخدمان mgr وcashier، كلمة المرور demo1234
cd api && npm i && npm run dev        # http://localhost:3000  (يستخدم erp_api@127.0.0.1)
cd web && npm i && npm run dev        # http://localhost:5173  (يمرّر /api إلى 3000؛ افتحه من الهاتف عبر شبكة الـ Wi-Fi نفسها)
# إنتاج بسيط: cd web && npm run build، ثم يخدمه الـ API نفسه من web/dist على المنفذ 3000
```

متغيرات الإنتاج: `DATABASE_URL`، `JWT_SECRET` (إلزامي)، `CORS_ORIGIN`، `PORT`.

## الاختبارات

```bash
cd api && npm test      # Vitest: يبني قاعدة erp_api_test من الصفر ويمرّ عبر HTTP فعليًا (31 اختبارًا)
```

## ما تغطيه الشريحة الأولى

| الشاشة | الملف | المسار في الـ API |
|---|---|---|
| الدخول | `Login.tsx` | `POST /auth/login` (عبر `fn_auth_lookup`، bcrypt، JWT لمدة 12 ساعة) |
| فتح الوردية | `OpenShift.tsx` | `POST /shifts/open` |
| البيع | `Pos.tsx` | `GET /pos/bootstrap`، `POST /sales` |
| تقرير الوردية والإغلاق | `Shift.tsx` | `GET /shifts/:id/report`، `POST /shifts/:id/close` |
| الفواتير: بحث، مرتجع، إلغاء | `Invoices.tsx` | `GET /invoices`، `GET /invoices/:id`، `POST /invoices/:id/return`، `POST /invoices/:id/reverse` |
| التعارضات (S48) | `Conflicts.tsx` | `GET /sync-conflicts`، `POST /sync-conflicts/:id/resolve`، `POST /sales/:id/credit-override` |

## قرارات تصميم

- **مسار بيع واحد للأونلاين والأوفلاين:** الهاتف يكتب الإيصال في الطابور المحلي ثم يرسله إلى `submit_offline_sale` (idempotent عبر `offline_uuid`). انقطاع الشبكة أو إعادة الإرسال لا يكرران الفاتورة ولا يخصمان المخزون مرتين.
- **الخادم يشتق الحسابات:** الجهاز يرسل طريقة الدفع والمبلغ فقط. الخادم يختار حساب الدرج أو المحفظة أو حساب العملاء، فلا يستطيع العميل اختيار حساب دفتر.
- **رفض الخادم لا يضيّع مبلغًا:** نقص المخزون أو تجاوز السقف أو إغلاق الوردية تعود `202` والإيصال محفوظ كـ `SYNC_CONFLICT`. أما الرفض الصريح (4xx) فينتقل الإيصال إلى «إيصالات رفضها الخادم» ولا يُحذف بصمت.
- **العدّ الأعمى:** من لا يملك `can_view_cash_balance` لا يرى النقد المتوقع لوردية مفتوحة.
- **RLS:** كل طلب في معاملة واحدة مع `app.current_tenant_id`، والاتصال بدور `erp_api` (عضو في `erp_app` فقط).
- **RTL:** `dir="rtl"` على مستوى المستند، وخصائص CSS منطقية (`inset-inline`، `margin-inline`)، وأرقام لاتينية متعمّدة لسهولة قراءة المبالغ.

## المرتجعات وإلغاء الفواتير

- **مرتجع جزئي بالكميات:** من تبويب «الفواتير». سعر الرد = ما دفعه العميل فعلًا للوحدة (بعد خصم السطر ونصيبه من خصم الفاتورة، مقرَّبًا للأسفل حتى لا يُرَدّ أكثر من المدفوع). الخادم يحسبه ويعرضه، والقاعدة ترفض تجاوز الكمية المباعة بشكل تراكمي.
- **طرق الرد:** نقدًا من درج وردية المستخدم، أو محفظة، أو على حساب العميل (إن كان على الفاتورة عميل).
- **تكرار الضغط آمن:** كل شاشة مرتجع تحمل `request_id` ثابتًا، فإعادة الإرسال تعيد المستند نفسه ولا تردّ مرتين.
- **إلغاء فاتورة كاملة (مدير فقط، تفرضه القاعدة):** يعيد المخزون والنقد بقيد عكسي. يختار الخادم تلقائيًا الوردية المفتوحة على صندوق الفاتورة. لا يُسمح به إن كان عليها مرتجعات مرحّلة، ولا يمكن إرجاع فاتورة ملغاة.
- **السياسة:** الكاشير يرجع من ورديته، والمدير من أي وردية. إن أردت اشتراط المدير للمرتجع أيضًا فهو سطر واحد في `routes/invoices.ts`.
- المرتجع يحتاج اتصالًا بالخادم، لأنه يعتمد على الفاتورة الأصلية.

## الأوفلاين (PWA)

- **Service Worker** (عبر `vite-plugin-pwa`): يخزّن قشرة التطبيق عند أول فتح، فيُفتح التطبيق وإعادة تحميله دون إنترنت. طلبات `/api` لا تُخزَّن ولا يجيب عنها الـ worker أبدًا. يتحدث التطبيق تلقائيًا عند نشر إصدار جديد.
- **IndexedDB** بدل localStorage: الطابور وكتالوج الأصناف والعملاء والإيصالات المرسلة. لا يظهر «حُفظ على الجهاز» إلا بعد اكتمال كتابة المعاملة فعلًا. ويُطلب `navigator.storage.persist()` لمنع إخلاء البيانات. تُرحَّل مرة واحدة أي بيانات قديمة من localStorage.
- **الإرسال:** عند عودة الاتصال أو كل 15 ثانية. وتعطّل التطبيق بين الحفظ والإرسال لا يضرّ لأن الخادم يتجاهل التكرار بـ `offline_uuid`.
- **الوردية:** الخادم يرفض (403) أي بيع على وردية ليست للمستخدم إلا للمدير، حتى لا يُنسب إيصال مخزَّن إلى شخص آخر سجّل الدخول على الهاتف نفسه.
- **التثبيت:** على Android يظهر «إضافة إلى الشاشة الرئيسية»، وعلى iPhone من زر المشاركة. الأيقونات وملف manifest (RTL، عربي) جاهزة.
- يلزم HTTPS في الإنتاج (أو localhost للتجربة) كي يعمل الـ Service Worker.

## تأمين الدخول

- **إقفال الحساب:** 5 محاولات فاشلة تقفل الحساب 15 دقيقة، حتى لكلمة المرور الصحيحة خلال الإقفال. المفتاح `الشركة:المستخدم`، والمستخدم غير الموجود يعامَل بنفس الطريقة تمامًا فلا يمكن اكتشاف الحسابات. وهناك حدّ إضافي لكل عنوان IP على مسارات الدخول (30 طلبًا في الدقيقة).
- **المصادقة الثنائية (TOTP):** تُفعَّل من شاشة «حسابي» بمسح QR. السر مشفّر AES-256-GCM في القاعدة، والرمز لا يُقبل مرتين (حماية من إعادة الاستخدام)، ويُسمح بانحراف ساعة ±30 ثانية. عند التفعيل تظهر 8 رموز استرداد مرة واحدة فقط، ويعمل كل رمز مرة واحدة. الخطأ في رمز التحقق يُحسب ضمن الإقفال.
- **كلمة المرور:** 10 أحرف على الأقل، حروف وأرقام، ولا تحتوي اسم المستخدم. تغييرها ينهي كل الجلسات الأخرى.
- **إبطال الجلسات:** كل طلب يتحقق من أن المستخدم فعّال وأن `token_version` لم يتغير. تغيير كلمة المرور أو تفعيل/إيقاف 2FA أو «الخروج من كل الأجهزة» أو تعطيل المستخدم يقطع الجلسات القديمة فورًا، لا بعد 12 ساعة.
- **سياسة الإلزام `REQUIRE_2FA`:** `none` | `managers` | `all`. الافتراضي في الإنتاج `managers`. من لم يفعّل 2FA وهو ملزم يحصل على جلسة محدودة لا تفتح إلا شاشة الإعداد (الواجهة تحوّله إليها تلقائيًا)، ولا يستطيع إيقافها بعد ذلك.
- **صلاحيات القاعدة:** دور التطبيق `erp_api` لا يقرأ `password_hash` ولا أسرار 2FA ولا رموز الاسترداد ولا جدول المحاولات، ولا يكتبها. كل ذلك عبر دوال `SECURITY DEFINER` محددة. ولا يستطيع التطبيق إنشاء مستخدمين.
- **ترويسات الأمان:** helmet (CSP وغيرها).

متغيرات البيئة: `JWT_SECRET` (إلزامي في الإنتاج)، `TOTP_ENC_KEY` (إلزامي في الإنتاج: يشفّر أسرار 2FA، وفقدانه يعني إعادة تفعيل 2FA لكل المستخدمين)، `REQUIRE_2FA`، `TRUST_PROXY=1` (خلف وكيل عكسي حتى يُقرأ IP الحقيقي)، `CORS_ORIGIN`.

## حدود معروفة

- أول تسجيل دخول يحتاج إنترنت، وكذلك فتح الوردية وإغلاقها وتقرير الوردية والتعارضات. البيع وحده يعمل دون اتصال.
- انتهاء صلاحية الجلسة (12 ساعة) دون اتصال: يبقى الطابور سليمًا ويُرسَل بعد تسجيل الدخول من جديد.
- وحدة القياس الأساسية فقط، والخصم على الفاتورة لا واجهة له بعد (الـ API يقبله).
- لا إلغاء لمرتجع من الواجهة (الدالة `reverse_sales_invoice` تدعمه)، ولا مرتجع للفواتير الضريبية (لا ضريبة في الواجهة بعد).
- لا مصادقة ثنائية ولا حدّ لمحاولات الدخول (مطلوبان قبل الإنتاج).
- الاتصال بقاعدة التطوير بكلمة مرور معروفة (`erp_api_dev`)، تُغيَّر في الإنتاج.
- لا توجد شاشة لإدارة المستخدمين بعد (إنشاء مستخدم، إعادة ضبط كلمة مرور أو 2FA، تعطيل). حاليًا تُنفَّذ من القاعدة بدور المالك.
- إعادة ضبط 2FA لمستخدم فقد هاتفه ورموز الاسترداد تحتاج تدخّل مسؤول القاعدة.
- التحقق بخطوتين يحتاج اتصالًا. من يملك جلسة مفتوحة يبقى يبيع أوفلاين، لكن الدخول الجديد يحتاج إنترنت.
